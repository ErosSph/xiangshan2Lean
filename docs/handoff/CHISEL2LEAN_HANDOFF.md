## 1. 已确定的决策与项目边界

### 1.1 已确定决策

| 编号 | 决策 | 实施含义 |
|---|---|---|
| D01 | 只做 Chisel → Lean 4 | 最终交付是自动生成的、可类型检查和执行的 Lean 硬件语义模型 |
| D02 | 保留参数及参数依赖 | 不仅保留名为 `n` 的字段，还要保留它对位宽、表达式、条件、数组和结构的影响 |
| D03 | 以 Chicala fork 为前端基础 | 优先复用其 Scala Typed AST 读取、Chisel 分析和可验证有用的 Pass |
| D04 | 使用明确的参数化语义 IR | 不能以无类型字符串、固定实例网表或直接拼接特定电路模板代替 IR |
| D05 | 从 IR 直接生成 Lean | 不要求先生成参数化 RTL，再依赖另一套工具恢复成 Lean |
| D06 | 官方 RTL 路线仅作独立参考 | 标准 Chisel 工具链及兼容的 CIRCT/RTL 工具用于实例化和行为对照 |
| D07 | 通用框架、分阶段支持 | Counter 是首个测试，不是最终任务范围；每个阶段公开支持范围和限制 |
| D08 | 不支持时明确失败 | 不允许默默省略硬件、替换为常量、假定复位或伪造符号参数 |

“在相应 Pass 之后接后端”不是要求无条件运行 Chicala 的所有现有 Pass。必须先确认哪些 Pass 保留必要语义，再确定接入位置和需要保留的源信息。

### 1.2 本项目要做

- 自动读取具有构建上下文的 Chisel 源码，获得类型化源级信息。
- 保留支持范围内的参数声明、合法性约束及参数相关表达式。
- 建立可执行的输入、输出、寄存器、组合逻辑和状态迁移模型。
- 处理支持范围内的位宽、符号性、截断、扩展、复位、使能和更新优先级。
- 逐步覆盖参数化数组、生成时分支/循环、辅助函数与模块层次。
- 建立诊断、来源定位、自动生成、Lean 编译/执行及独立行为对照测试。

### 1.3 明确不做

- 不做 AI Agent，也不搭建 LLM 证明/修复循环。
- 不做自然语言规格自动形式化。
- 不做电路功能定理自动生成、归纳不变式发现、定理证明流水线。
- 不做证明指导库、可复用引理检索库。
- 不复现 CircuitProver 的 63/63、Rtl2lean 的定理数量或模型实验指标。
- 不开发参数化 SystemVerilog 后端，不把 Sparkle 设为必经依赖。
- 不改造 CIRCT 作为当前主任务，不从源码全量构建 LLVM/CIRCT 来启动项目。
- 不进行 FPGA 部署、综合性能优化、AIE/ORCA/SRAD 等其他项目工作。

Lean 类型正确性所需的小型辅助定义、已有定理的必要应用，以及用于测试的断言，不等于建设“自动证明系统”。但不能以此为由扩展出论文 Phase II/III。

## 3. 输入、输出与正确性目标

### 3.1 输入不只是一个孤立字符串

输入应包括：Chisel `.scala` 文件、模块选择、源码依赖、Scala/Chisel 构建配置，以及区分“要保留的参数”和“已固定环境配置”所需的信息。

目标是读取 `Counter(n: Int)` 这种**生成器定义**，而不是仅分析 `new Counter(8)` 之后得到的具体电路。模块选择与符号参数声明的命令行/API 形式在 T1 中确定；当前没有已经实现的 `chisel2lean` 命令。

### 3.2 目标输出

输出是 `.lean` 源码和必要的少量运行时支持定义。一个时序模块预期具有以下概念接口，名称可在 IR/后端设计时统一：

```text
Params                  参数与合法性条件
Inputs(p)               输入，允许宽度依赖参数
State(p)                寄存器/数组/子模块状态
Outputs(p)              输出，允许宽度依赖参数
step(p, inputs, state)   单个约定时钟边沿的下一状态
output(p, inputs, state) 当前采样约定下的组合输出
resetState / init        仅在源语义和初始化约定支持时提供
```

接口必须满足下列要求：

- `State(p)` 中的位宽能保留为 `BitVec (widthExpr p)`，而不是只生成 `BitVec 8`。
- 参数化数组能用例如 `Fin n → BitVec w` 或其他等价、可执行的表示；具体选择待定。
- `output` 不能一概只接受 `state`：组合输出可能依赖当前输入。
- 组合电路可以没有实际寄存器状态，不要为了接口统一伪造寄存器。
- 生成文件应有明确 namespace、来源信息和稳定名称，并记录依赖的运行时版本。
- 不要通过 `sorry`、`admit`、新增公理或不透明外部行为来填补缺失的硬件语义。

### 3.3 我们要保证的对应关系

对一个已接受的源模块 D，在支持的参数、输入和状态语义范围内，目标是：

```text
运行生成的 Lean 模型实例 Lean(D, p)
与
运行标准 Chisel 生成的硬件实例 RTL(D, p)

在对齐的输入序列、状态对应关系、复位和采样约定下，得到一致的可观察行为。
```

这是**翻译的语义保持目标**，不是声称已经有其形式化证明。

区分四种不同结果：

| 结果 | 能说明什么 |
|---|---|
| Chicala 示例编译成功 | 前端构建/转换路径在该用例上可运行 |
| 生成的 Lean 类型检查成功 | 输出程序类型正确 |
| 参数表达式和结构仍存在 | 获得参数化表示，但不自动证明语义正确 |
| 与独立 RTL 在已测配置一致 | 有差分测试证据；不能推出所有参数均已形式化验证 |

## 4. 确定架构与组件职责

```text
                   Chisel 源码 + 构建上下文
                              │
             ┌────────────────┴────────────────┐
             │                                 │
       主线：我们的翻译器                 独立参考：标准工具链
             │                                 │
       Chicala Typed AST                  固定合法参数 p
             │                                 │
       审查后保留/调整的 Pass              标准 Chisel 展开
             │                                 │
       参数化语义 IR                    兼容的 RTL 编译路径
             │                                 │
       Lean 4 后端                         具体 RTL 仿真
             │                                 │
       参数化 Lean 模型                         │
             │                                 │
       以相同 p 实例化                         │
             └────────────────┬────────────────┘
                     输入/复位/采样对齐后比较
```

主线不得退化为“先固定参数生成 RTL，再猜回 `n`”。官方 RTL 路线仅作参考，不承担参数保留责任。

### 4.1 Chicala fork

复用能实际审查和测试的前端能力，不把整个研究原型当作可信黑盒。保留上游来源和已有输出模式，避免为新增 Lean 后端大面积破坏原功能。

### 4.2 参数化语义 IR

IR 应从前端信息中提取并规范化硬件语义，而不是简单重命名现有 AST。允许首版围绕 Chicala AST 增加小型适配层，不要求先造庞大的通用编译基础设施。

必须区分两种层次：

- **生成时语义**：Scala 参数计算、参数相关 `if`、循环、模块构造。
- **电路运行时语义**：`when`、组合计算、寄存器旧状态和下一状态。

同时保留表达式类型、宽度、来源位置及必要的参数合法性条件。错误可以回溯到原 Chisel 文件和构造。

### 4.3 Lean 后端

从已规范化的 IR 生成可执行 Lean 定义。常见位向量、状态与数组操作可以使用小型运行时语义库。这个库只承载翻译语义，不是证明知识库。

后端实现语言尚未冻结。T0 后优先评估在现有 Scala 工程内实现 IR/Emitter，以减少跨进程序列化成本；Python 可用于测试和辅助脚本，不要求将完整后端重写为 Python。

### 4.4 官方 Chisel/CIRCT 参考路径

使用与测试源码匹配的官方工具链版本。**Chicala 的 Chisel 3.5.6 基线不意味着可以直接套用现代 Chisel 的全部 CIRCT 调用方式。**T0 需要调查兼容路径，不能为了采用最新 `firtool` 而擅自升级整个前端。

如旧基线的标准参考路径使用其配套 FIRRTL 编译器，应记录这一事实。CIRCT 的接入方式是参考环境的兼容性问题，不是改变直接 Chisel → IR → Lean 主线的理由。

不得只比较我们自己两个后端的结果；共享错误 IR 的两个后端可能产生一致的错误。参考 RTL 必须来自原始 Chisel 和标准工具链，且不依赖我们的 Lean 翻译结果。

## 5. 语义风险与 IR 必须记录的信息

本节是待实现的工程约束，不代表 Chicala 已经支持这些语义。具体转换规则需要以选定版本的源码和实验为准。

| 领域 | 必须明确的内容 | 不能采用的捷径 |
|---|---|---|
| 参数类型 | Scala `Int`/其他宿主类型的取值域、运算、合法性检查 | 把所有 `Int` 无条件变成无界 `Nat` |
| 参数表达式 | `n`、`n+1`、`2*n`、条件、取整、辅助函数等依赖 | 用一个巨大常量替换 n 后文本恢复 |
| 位宽 | 操作数与结果宽度、推导、扩展、截断、零宽边界 | 只把 `+` 打印成 Lean 的 `+` |
| 符号性 | `UInt`/`SInt` 的比较、扩展、移位解释 | 只保存位模式、不区分运算解释 |
| 寄存器 | 旧状态读取、下一状态表达式、保持分支 | 在模型中按顺序立即覆盖寄存器 |
| 赋值优先级 | 条件嵌套、后续连接覆盖、默认连接 | 按 AST 遍历顺序随意生成互不相关的 if |
| 复位 | 同步/异步、极性、条件、复位值、作用域 | 统一补一个最高优先级的 reset |
| 初始化 | 已知复位状态与未知上电状态的区别 | 将所有未复位寄存器初始化为零 |
| 输出 | 当前输入依赖、状态依赖、边沿前后采样 | 把所有输出都视为下一状态 |
| 生成结构 | 参数控制的分支、循环、数组大小和模块数量 | 只保留某个参数实例执行过的分支 |
| 模块层次 | 参数映射、接口连接、子模块状态组成 | 扁平化时丢失源级映射或复制共享状态 |
| 未支持行为 | 相关外部调用、BlackBox、存储器、多时钟等 | 静默忽略或生成随意默认实现 |

### 5.1 需要在交接中明确的初始化约定

之前讨论曾用 `init = 0` 示意 `RegInit`。正式实现不能把该示意当作所有电路的真实上电语义。

Chisel 的 `RegInit` 指定寄存器在当前隐式复位有效时的值。[S7] 对于本项目的首个同步复位计数器，可选择“执行一次有效复位后开始观察”的测试约定；此时 `resetState` 可以是零状态。

但对于未复位寄存器、部分复位状态，或异步复位，必须另行建模或明确拒绝。源代码不能提供确定初态时，优先让 `step` 接受外部给定的任意状态；不能为了凑齐 `init` 接口而增加硬件没有的假设。

### 5.2 参数值与 Lean 自然数

`BitVec` 的宽度需要自然数表达式，但这不等于 Chisel 中参与宽度计算的宿主参数天然具有无界自然数语义。选择宽度映射时，要处理合法范围和参数运算的对应关系。Lean `Nat` 本身没有固定上界。[S8]

首版可以在文档化、可检查的合法参数域中支持正宽度；不能擅自把源程序允许的行为删除后称为“完整保留任意参数”。暂不支持的参数域必须作为能力限制公开，而不是隐藏成断言。

### 5.3 通用性的工作定义

最终方向是可扩展、面向多种 Chisel 设计的翻译器，不是识别模块名字的脚本。阶段性支持范围必须以“语法/语义构造”定义，并用不同电路检验。

对暂不支持的、与硬件生成结果有关的 Scala 计算，输出可定位错误。不要因为工程中存在无关的打印或测试代码就一概拒绝整个项目；需要分析目标模块的相关依赖范围。

## 7. 当前任务卡：T0-CHICALA-FRONTEND-AUDIT

### 7.1 任务目标

确认 Chicala 能在什么阶段、以什么结构，为我们的参数化 IR 提供参数、类型、寄存器和状态迁移信息；建立可运行的原始转换基线；据此确定 Lean 后端接入点。

T0 的交付重点是“有证据的工程判断”，不是把后端写出来。

### 7.2 第一步：工作区与环境确认

在用户选定的项目目录中，读取现有 `AGENTS.md`、本文和已有项目文档，确认实际仓库边界。

记录工作目录、分支、HEAD、`git status`、现有修改、远程地址、操作系统、JDK、sbt、Scala、Lean/Lake 是否可用。不存在的工具就记为未安装，不虚构版本。

没有明确工作区、目录属于另一个项目，或准备写入的位置有冲突时，先确认该具体问题。不得自行采用其他项目的路径、主机、SSH 会话或仓库。

用户已同意基于 Chicala fork 开发，但 GitHub 目标 owner/仓库尚未指定。没有远程 fork 也可以先做本地副本审查；不能声称已创建远程 fork。远程创建、发布和推送前需要明确目标和授权。

### 7.3 第二步：建立上游来源与版本记录

优先从本文件记录的提交建立独立审查副本。若实际已有仓库或提交不同，记录差异后继续判断，不得对现有工作树强行 `reset --hard` 或删除修改。

保存上游 URL、提交、构建依赖和原始文件校验信息。保留许可证和来源文件，不把第三方工程改成无来源的代码片段集合。

不要默认升级 Scala/Chisel。先确认原项目能否工作，再决定是否确实需要最小兼容修复。

### 7.4 第三步：审查真实前端和 Pass

以下路径是审查入口。转换入口已在本次远程核对中读取；其他子模块仍需逐项定位和检查，不能因为列在此处就算审查完成。

| 路径（相对于 Chicala 根目录） | 要回答的问题 |
|---|---|
| `src/main/scala/chicala/ChicalaPlugin.scala` | 插件注册、选项与阶段配置是什么？ |
| `src/main/scala/chicala/convert/ChiselToScalaComponent.scala` | Typed AST 在何时进入？Pass 和 Emitter 在哪里连接？ |
| `src/main/scala/chicala/convert/frontend/Scala2Reader.scala` | Reader/Loader 的组织方式与扩展边界？ |

重点审查 `LiteralPropagation`、`RegEnableApply`、`SubModuleCall`、`DependencySort`。记录 Pass 之前/之后的相关结构；不能仅检查最终 `Params` 字段是否还叫 `n`。

### 7.5 第四步：运行原始编译/翻译基线

先读构建脚本，再执行确认过的任务。上游 README/Makefile 提供 `sbt publishLocal` 和 `make test`，但它们是待在实际环境验证的命令，不是本交接已经运行成功的命令。[S2][S6]

注意 `make test` 会清理测试子工程编译产物；在隔离副本中执行并保留必要的旧证据。不要运行会删除已有实验记录的清理命令。

每次尝试保存命令、工作目录、开始/结束时间、退出码、stdout、stderr、变更列表和生成文件。编译失败要保留真实错误，不用一个手写 Lean 示例替代失败的前端实验。

无需安装或运行 Stainless。原始 Scala 输出本身能否仿真，与 Chisel 翻译能否完成分开记录。

### 7.6 第五步：少量有针对性的源级探针

在单独的 audit fixtures 中添加小型 Chisel 用例，不要改掉原测试电路来假装上游支持。

| 探针 | 检查内容 | T0 要保存的证据 |
|---|---|---|
| 参数化 Counter | `n`、require、UInt(n.W)、RegInit、when、输出 | 源码、Typed AST、内部结构、Pass 后输出 |
| 双寄存器更新 | 一个寄存器读取另一个寄存器的旧值 | 旧状态与下一状态是否分离 |
| 优先级更新 | 默认连接、嵌套/连续条件赋值 | 优先级信息在哪一层被表示或改变 |
| 参数分支 | Scala `if (n > k)` 与硬件 `when` 的区别 | 两个生成分支是否仍在、条件是否符号化 |
| 参数化 Vec/循环 | n 决定状态数量/生成数量 | 结构表达能力或明确的失败位置 |
| 参数辅助表达式 | `n+1`、`2*n` 或简单辅助函数 | 参数类型、宽度计算及潜在溢出处理 |

探针不要求全部成功。出现缺口是有价值的审查结果：需要记录“哪里不支持、为什么、后续改哪层”。

允许为保存 AST/Pass 中间结果增加**最小、隔离、可撤销的调试输出**；必须登记 diff。T0 不借机改写核心语义或大规模修复全部探针。

### 7.7 第六步：给出可实施的接入结论

最终报告必须明确回答：

1. 参数、约束、位宽表达式分别保存在哪个类型和字段中？
2. RegInit、when、保持分支、赋值优先级和输出连接是否充分表示？
3. 哪些 Pass 可以复用，哪些需要绕过、补充元数据或修改？
4. 推荐在何处构造参数化 IR，为什么不是更早或更晚？
5. 直接新增 Lean Emitter 是否足够，还是需要前端/IR 改造？
6. 首批可实现构造、暂不支持构造以及兼容性风险是什么？
7. M1 应新增/修改哪些具体文件？最小变更是什么？

结论可以是“有条件可复用”或“关键结构需补齐”。不允许为迎合既定路线而把未支持行为写成已支持。

## 8. 后续翻译质量测试原则

以下是 M1–M4 的测试要求，不是让 T0 立即实现所有功能。

### 8.1 自动化而非模板硬编码

不能以模块名、变量名或完整源码匹配来挑选一个手写 Lean 模型。对 Counter 重命名、修改增量、调整输入/输出名称后，转换器仍应依据 AST/IR 正确生成代码。

手工 IR 可以用于单元测试，但端到端验收必须从真实 Chisel 源码开始；不允许人工修订生成的 `.lean` 后再计为转换成功。

### 8.2 参数与构造覆盖

先测小参数、临界值和非典型值，例如在合法范围内选 `1、2、3、4、7、8、9`。对 `n > 8` 之类条件，必须覆盖阈值两侧；不能只测 2 的幂。

数组长度、算术宽度、分支门限是不同参数使用模式，不能只用多个 Counter 位宽代表全部参数化能力。

### 8.3 单步和多周期对齐

对于寄存器电路，统一以下约定并写进测试元数据：输入施加时刻、时钟边沿、复位类型和长度、输出在边沿前还是后采样、初态/复位后的状态对应关系。

只有能够合法设置或通过输入到达某状态时，才能声称 RTL 参考覆盖了该状态。没有内部状态控制方法时，不要把“枚举了数学状态”误写成“RTL 穷举测试了所有状态”。

观察到的内部寄存器名可能被标准工具优化；优先比较接口行为，内部状态比较需有明确且不改变行为的映射方式。

### 8.4 不要自动修复源电路

如果源 Chisel 中的使能/复位优先级有设计错误，转换器应保留其实际行为，而不是把它改成我们认为正确的计数器。设计是否符合人的规格不属于当前任务。

测试中可故意构造行为不同的源程序，确认生成的 Lean 会随之不同；也可对转换器进行局部错误注入，确认差分测试能够报警。

### 8.5 证据与报告

每个回归结果记录工具版本、参数、输入种子/序列、比较范围、采样约定、退出码和差异。小配置穷举与大配置随机测试分别统计，不能混称“穷举”或“形式化证明”。

## 9. 实现难度、风险与资源安排

整体是**中高难度的编译器与语义建模工程**。下面是规划判断，不是上游项目承诺，也不是已经测量出的工期。

| 子任务 | 难度判断 | 风险控制 |
|---|---|---|
| 旧版环境与上游基线 | 中等 | 固定提交/依赖；不先升级语言版本 |
| 读取参数和现有 AST | 中等 | 复用 Loader；结合真实探针，不靠 README 推断 |
| IR 语义与类型设计 | 高 | 明确生成时/运行时和宽度规则；小步演进 |
| 基础 Lean 代码生成 | 中等 | 从类型化 IR 生成，检查名称/依赖/可执行性 |
| 位宽、符号与多重连接 | 高 | 为每个构造做边界和差分测试 |
| 参数化结构与子模块 | 很高 | 分阶段覆盖，保留结构而不是具体展开后回推 |
| 独立语义回归 | 高 | 参考路径与主线隔离，统一初态和周期约定 |

前文讨论过：在已有相关基础且较集中投入的情况下，有限子集稳定原型可暂按 2–4 个月量级规划；对 Scala/Lean/编译器初学者可能是 4–8 个月或更久。**这些只保留为早期量级估计，不作为 deadline；完成 T0 后必须按真实缺口重新评估。**

不应为“完整任意 Scala/Chisel 程序支持”给一个短期完成承诺。长期通用方向不变，实际声明以版本化支持范围为准。

优先把时间投入语义和可复现测试，不先搭建大型插件系统、复杂服务、GUI、证明数据库或新硬件编译栈。
