## 建议的目标框架

```text
README.md                         项目入口、最短路径、当前成熟度
docs/README.md                    文档导航和“看哪份文档”索引
docs/architecture/                组件图、语义边界、接口与设计决策
docs/guides/                      安装、转换、运行和扩展示例
docs/operations/                  本地/服务器流程、迁移、发布与协作
docs/validation/                  验证目录、范围说明和证据索引
docs/history/                     历史交接和已结束阶段记录
python/chisel2lean4/              按子系统组织的 Python 实现包
  frontend/                       FIRRTL、Yosys、四态等前端
  ir/                             共享中间表示及转换边界
  backend/                         Lean 生成与执行适配
  tooling/                        配置、报告和服务器辅助工具
scripts/                          常用 CLI、共享模块和阶段指纹扫描器
src/main/scala/chicala/           现有 Chisel/Scala 前端插件
lean/Chisel2Lean/                 现有 Lean runtime 与执行模型
tests/{unit,integration,fixtures}/按测试意图组织测试和小型夹具
verification/                     可复现验证输入、桥接模型和用例
experiments/                      按原路径保留的运行记录、快照和原始证据
```

这是逻辑目标，不要求一次性创建所有目录。Scala 源码仍由当前 `build.sbt` 管理；包名采用 `chisel2lean4`，避免和现有 `scripts/chisel2lean.py` 模块名冲突。当前 Python 包按仓库源码目录导入，尚未安装成独立 wheel。

## 分阶段清单

### 0. 锁定保护边界

- 记录本轮文件状态、公开 CLI、模块导入方式和文档内链接；只读分析，不重置、清理或覆盖工作区。
- 把已修改文件和未跟踪证据当作用户资产；任何搬迁先核对文件归属、哈希及引用。
- 保留二态默认入口、四态独立入口、现有 Scala/Lean 工具链和所有历史验证结论。

### 1. 建立文档入口和事实源

- 新建 `docs/README.md`，按“开始使用 / 架构 / 验证证据 / 服务器操作 / 历史交接”分流，并说明各文档的权威范围。
- 精简根 `README.md` 为项目定位、快速开始、当前状态和文档入口；把重复的长篇介绍指向一份主文档。
- 增加短小的当前状态页，单独列出已验证、正在做、阻塞项和下一步；历史报告只追加，不改写旧结论。
- 四态设计、接口、支持范围、证据和阻塞项按仓库规则继续以 `docs/fourstate-frontend.md` 为唯一详细来源；为长文档加目录，并由状态页链接到它。保留现有章节锚点，不把阶段证据搬出该文件。
- 建立验证报告索引，注明报告的对象、输入/工具版本、执行状态、比较范围和局限。JSON/CSV 暂不批量移动。

### 2. 给脚本加清晰边界

- 先按功能和调用关系给 206 个脚本分类：公共 CLI、转换/前端、Lean 生成/运行、四态独立前端、香山/服务器适配、一次性验证。
- 识别直接调用路径、`sys.path` 假设、脚本间导入、文档命令、测试引用和外部自动化依赖。
- 将稳定实现逐批迁入 Python 包；保留常用转换 CLI 原路径，验证/实验脚本从分类目录直接运行。
- 把一次性验证驱动与产品代码分开；不将研究脚本误删，也不为了目录整齐改写原始实验记录。
- 将公共二态核心、四态前端和验证/报告工具的依赖方向画清楚，禁止四态实验悄然改变默认二态流程。

### 3. 整理验证与夹具

- 按单元、集成、端到端和故障注入分类测试；小型可复用输入进入 `tests/fixtures/` 或 `verification/`。
- 原始生成物和大体积实验输出继续留在现有 `experiments/` 路径，索引链接到它们；不通过移动或重命名改变证据路径。
- 统一验证记录的元数据字段：命令、退出码、源/工具哈希、比较对象、样本范围、结论和已知限制。
- 只调整当前仍在使用的文档与测试引用；旧报告作为历史证据保留原文。

### 4. 兼容性门槛和收尾

- 每批迁移都核对实际保留的命令入口、模块导入、硬编码路径和证据打包约定。
- 文档迁移后检查所有 Markdown 链接、仓库内硬编码路径、Python 导入、构建入口和验证入口。
- 用户明确授权后可删除不再需要的兼容桥接；实验数据和历史报告不随代码迁移删除。
- 汇总实施变更、未实施项和实际执行过的回归；不把计划中的检查写成已通过结果。

## 初始建议顺序（后续执行已调整）

1. 先补 `docs/README.md` 与当前状态页，并修正根 README 的过时导航。
2. 产出脚本分类表和调用/导入图，不移动脚本。
3. 从低耦合的一个脚本子集开始迁入包，并明确保留哪些公共入口。
4. 等路径引用审计稳定后，再决定是否拆分长篇四态文档或归档历史交接材料。

这样可以先改善可读性和协作入口，再用实际依赖证据决定代码迁移边界。

## 暂不纳入的变更

- 不改硬件语义、IR 格式、Lean runtime、共享后端或默认 CLI 行为。
- 不删除或覆盖现存报告、`experiments/`、`runs/` 和生成证据；本轮获授权删除的 101 个旧根目录桥接脚本除外。
- 不更改服务器、安装软件、提交或推送 Git。
- 不把历史阶段性 PASS 合并成更广的等价性结论。

若后续方案需要改公共后端、IR、runtime 或 CLI 接口，应先把精确范围、兼容策略和必要回归写入本计划，再按仓库协作规则与用户确认后实施。
